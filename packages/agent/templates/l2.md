# Level: L2 — Service

You are at the service level. This is where code lives. Work here directly.

## What L2 Is
- An actual codebase — the app, API, crawler, or tool
- Git submodule of an L1 wizrd (or standalone for company services like `services/website/`)
- Has its own CLAUDE.md with service architecture, patterns, conventions
- This is where you read code, write code, run tests, create PRs

## What You Can Do at L2
- Read and modify code
- Run dev servers, tests, linters
- Create/manage branches and PRs
- Write worklogs at `worklog/`
- Read the service CLAUDE.md for patterns and conventions

## Rules
- **Use worktrees** — always create a worktree before making changes
- **Follow existing patterns** — read the codebase before suggesting changes. Look at how similar features are implemented.
- **Tests required** — write tests for new functionality
- **PR conventions** — descriptive title, summary with "why", test plan

## Before Making Changes
1. Read CLAUDE.md if it exists — service architecture, stack, patterns
2. `git fetch --all && git branch -a` — know what branches exist
3. `git log --oneline -10` — recent activity
4. If working on a feature branch: `git log origin/main..{branch} --oneline` — what's already done

## Branch Investigation Checklist
When asked about a branch or feature:
1. `git log origin/main..{branch} --oneline` — how many commits? (NOT `gh api`)
2. `git diff origin/main..{branch} --stat` — what files changed?
3. `git diff origin/main..{branch} -- {specific-files}` — read the actual changes
4. If branch has many commits from drift: `git log origin/main..{branch} --oneline --author={name}` to filter

## Git Workflow
```bash
# Start work
git fetch --all
git checkout -b feat/my-feature origin/main

# Sync feature branch with main (merge, not rebase — safe for shared branches)
git fetch --all
git merge origin/main --no-edit

# Check what your branch adds vs main
git log origin/main..HEAD --oneline
git diff origin/main --stat

# Push
git push -u origin feat/my-feature
```

## Common L2 Mistakes to Avoid
- **Don't diff before counting commits** — a branch forked from old main may show hundreds of changed files that aren't relevant
- **Don't use `gh api` for diffs/commits** — you're in the repo, use git
- **Don't assume the branch name** — check `git branch -a` first
- **Don't start coding without reading existing patterns** — the codebase has conventions
- **Don't push to main** — always use feature branches and PRs
